审计对象：`d:\kefu\kefu`

目标系统：二维码扫码进入的在线客服聊天系统

审计日期：2026-05-06

## 一、项目技术架构分析

### 1. 当前技术栈

- 后端语言：PHP，`composer.json` 要求 `php >= 5.4.0`
- 后端框架：ThinkPHP `5.0.24`
- 数据库：MySQL，安装 SQL 来源为 `install/data.sql`
- WebSocket：Workerman 自建 Pusher 协议兼容服务
- 前端：传统 jQuery、Layui、Bootstrap，局部使用 Vue
- 缓存：默认文件缓存，未发现业务层 Redis 使用
- 上传/存储：本地、阿里云 OSS、腾讯云 COS、七牛云等存储适配
- 微信能力：EasyWeChat，用于公众号、模板消息、临时二维码等

### 2. 项目结构

项目主体为 ThinkPHP 多模块结构：

- `application/admin`：客服后台、会话、消息、访客、上传等核心业务
- `application/platform`：平台管理后台、商户管理、插件、配置
- `application/index`：访客 H5 聊天入口
- `application/mobile`、`application/mapp`：移动端客服/访客相关入口
- `application/common`：公共方法、存储、云更新、工具类
- `ymwl_pusher`：独立 Workerman WebSocket 推送服务
- `install`：数据库安装脚本
- `public/assets`：前端静态资源、编辑器、JS/CSS

结构能体现 MVC，但业务逻辑大量集中在 Controller 中，例如 `application/admin/controller/Event.php` 和 `Set.php`，Service 层不足，接口规范不统一，路由配置很弱。存在重复前端目录 `admin`、`admin1`，以及运行缓存、旧版 min 文件、插件和编辑器遗留代码。

### 3. 架构结论

该项目适合作为“在线客服业务原型”参考，但不适合作为高并发、长期维护、强安全要求的二开底座。

建议：保留业务概念和部分后台页面，重写实时通信、鉴权、上传、消息协议、二维码渠道和数据库核心模型。

## 二、WebSocket 审计

### 1. 使用方案

项目使用 Workerman，不使用 GatewayWorker、Swoole、socket.io。

核心文件：

- `ymwl_pusher/start.php`
- `ymwl_pusher/src/Pusher.php`
- `ymwl_pusher/config.php`
- `application/common/lib/SinglePusher.php`
- `application/extra/push/Pusher.php`
- `application/admin/controller/Event.php`
- `application/admin/view/public/header.html`
- `application/index/view/index/index.html`
- `application/mobile/view/index/index.html`

### 2. 启动方式

WebSocket 入口为：

```bash
php ymwl_pusher/start.php start
```

Windows 下还有：

```text
ymwl_pusher/winstart.bat
```

`start.php` 中创建：

- WebSocket 监听：`websocket://0.0.0.0:$websocket_port`
- HTTP API 监听：`http://0.0.0.0:$api_port`
- Worker 数：`$pusher->count = 1`

### 3. 消息分发流程

1. 访客或客服通过 HTTP 接口发送消息。
2. ThinkPHP 控制器写入 `wolive_chats`。
3. 控制器调用 `SinglePusher::getinstance()->trigger(...)`。
4. PHP Pusher 客户端向 `ymwl_pusher` 的 HTTP API 端口发送事件。
5. `ymwl_pusher/src/Pusher.php` 根据频道发布 WebSocket 帧。
6. 浏览器端 `pusher.min.js` 收到事件并更新界面。

常见频道：

- `kefu{service_id}`：客服个人聊天频道
- `cu{channel}`：访客聊天频道
- `all{business_id}`：商户广播频道
- `ud{service_id}`：客服个人通知频道

常见事件：

- `cu-event`
- `my-event`
- `check-event`
- `on_notice`
- `logout`
- `geton`
- `getswitch`
- `video`
- `video-refuse`
- `push-comment`
- `first_word`

### 4. 是否真正实时

是真 WebSocket，不是 AJAX 轮询冒充。

但项目同时存在大量 AJAX 辅助接口，例如获取会话列表、等待队列、访客资料、历史消息等。这些 AJAX 不是聊天主链路的替代，而是 UI 和列表刷新辅助。

### 5. 主要问题

- WebSocket 服务单进程，在线状态和订阅关系都在内存。
- 进程重启会丢失在线态。
- 无 Redis、无共享状态，不能多机水平扩展。
- API 端口若暴露公网，存在伪造广播风险。
- 当前很多频道为 public channel，`authEndpoint` 对核心频道约束不足。
- `socket_id` 排除发送方逻辑存在实现瑕疵。
- Flash WebSocket 兜底代码已经过时。

### 6. WebSocket 结论

短期小规模演示或内部使用可以保留；如果要做正式客服系统，建议重写实时通信层。

推荐路线：

- Workerman + GatewayWorker + Redis
- 或 Swoole WebSocket + Redis
- 或独立 Node.js/NestJS WebSocket 网关 + Redis

## 三、安全审计

### 1. 危险函数扫描

项目自有代码中未发现典型恶意：

- `eval`
- `system`
- `exec`
- `shell_exec`
- `passthru`
- `proc_open`
- `assert`
- `create_function`
- `gzinflate` 恶意组合

命中点主要为：

- `application/common.php` 中 `base64_decode` 用于自定义加解密。
- `public/assets/ueditor*/php/Uploader.class.php` 中 `base64_decode` 用于 base64 图片上传。
- `application/common/lib/CurlUtils.php` 中 `exec()` 是类私有方法名，内部是 `curl_exec`，不是系统命令执行。

未发现 ionCube、SG11、Zend Guard 加密特征。

### 2. 高危风险文件

#### `public/install.php`

风险：

- 使用 `extract($_POST)`、`extract($_GET)`，存在变量覆盖风险。
- 安装阶段 SQL 拼接，存在 SQL 注入风险。
- 可写入入口文件、数据库配置、Pusher 配置。
- 若部署后未删除，风险极高。

处理建议：

- 生产环境必须删除。
- 如需保留安装器，应移出 Web 根目录。
- 所有 SQL 改为参数绑定。
- 禁止 `extract`。

#### `config/database.php`

风险：

- 明文数据库账号、密码、库名、主机。

处理建议：

- 改为 `.env`。
- 禁止提交真实生产凭据。
- 立即轮换已暴露密码。

#### `ymwl_pusher/config.php`

风险：

- 明文 `app_key`、`app_secret`、域名、端口。

处理建议：

- 改为环境变量。
- API 端口只监听 `127.0.0.1` 或通过防火墙限制。
- 已泄露密钥应立即更换。

#### `application/common/lib/cloud/CloudUpdate.php`

风险：

- 可远程下载 zip。
- 解压覆盖项目目录。
- 存在 `update.sql` 时执行 SQL。
- 下载时 TLS 校验关闭。

处理建议：

- 正式二开建议删除远程更新模块。
- 如保留，必须增加签名校验、白名单、权限隔离、审计日志。

#### `application/platform/controller/Addons.php`

风险：

- 插件 ZIP 上传和解压存在 Zip Slip 风险。
- 插件安装具备高权限执行能力。

处理建议：

- 禁用在线插件安装。
- 解压前校验路径，禁止 `../` 和绝对路径。
- 插件源必须签名。

#### `application/admin/controller/Event.php`

风险：

- `header('Access-Control-Allow-Origin:*')` 跨域过宽。
- 聊天 HTML 内容过滤不完整。
- 图片、链接、文件消息以 HTML 片段方式拼接和存储。
- 存在调试残留如 `var_dump`。

处理建议：

- 改为结构化消息协议。
- 文本、图片、文件、音频、视频分别存类型和 metadata。
- 前端渲染时统一转义。
- 上传文件名、URL、HTML 属性全部过滤。

### 3. XSS 风险

项目多处把聊天内容、商品卡片、文件链接、图片 HTML 直接拼入页面。例如：

- `application/admin/controller/Event.php`
- `application/index/controller/Index.php`
- `application/index/view/index/index.html`
- `application/mobile/view/index/index.html`

建议：

- 禁止直接存 HTML 作为消息正文。
- 使用 `type + payload` 消息结构。
- 文本统一 `htmlspecialchars`。
- URL 必须做协议白名单。
- 图片/文件只保存后端生成的资源 ID 或安全 URL。

### 4. 上传风险

上传模块允许：

- 图片
- 文档
- 压缩包
- 音视频
- APK

风险点：

- 主要依赖扩展名校验。
- 附件与聊天消息缺少强关联。
- 缺少病毒扫描、MIME 校验、私有桶权限控制。

建议：

- 文件统一走对象存储。
- 只允许业务必须类型。
- 服务端校验 MIME、扩展名、文件头。
- 文件名重写。
- 下载走鉴权接口或短期签名 URL。

### 5. 安全结论

未发现明显木马或加密后门，但存在多个高危工程安全问题。当前代码不建议直接上线二开。

风险等级：高。

## 四、数据库结构审计

### 1. 核心表

#### `wolive_business`

商户表，保存商家名称、Logo、域名、分配规则、音视频开关、模板消息开关、状态等。

#### `wolive_service`

客服/员工表，保存客服账号、密码、昵称、分组、角色、在线状态。

问题：

- 密码字段需要确认加密方式。
- 角色模型较粗。
- 在线状态直接存在 DB，不适合高并发实时状态。

#### `wolive_visiter`

访客表，保存访客 ID、昵称、头像、IP、来源 URL、openid、在线状态、访问次数等。

可复用点：

- 访客档案。
- H5 访客身份。
- 微信 openid 绑定。

不足：

- 无设备表。
- 无二维码渠道字段。
- 无用户画像扩展表。

#### `wolive_queue`

会话/排队表，保存访客、客服、分组、商户、状态、最后消息时间。

问题：

- 无独立 `session_id`。
- 会话历史边界不清晰。
- 黑名单被混在 `state` 中。

#### `wolive_chats`

消息表，字段包括：

- `cid`
- `visiter_id`
- `service_id`
- `business_id`
- `content`
- `timestamp`
- `state`
- `direction`
- `unstr`
- `avatar`

问题：

- 存储引擎为 MyISAM。
- 内容为 `mediumtext`，消息类型不结构化。
- 图片、文件、HTML 混在 `content` 中。
- 无会话 ID。
- 无投递状态、撤回状态、删除状态。
- 已读未读只有简单 `state`。

#### `wolive_attachment_data`

附件归档表，但与 `wolive_chats.cid` 无强关联。

#### `wolive_reply`、`wolive_question`、`wolive_sentence`

快捷回复、常见问题、欢迎语相关，可作为二开复用。

#### `wolive_wechat_platform`、`wolive_weixin`

微信公众号配置和微信用户绑定，可参考复用。

### 2. 缺失表

建议新增：

- `qr_channels`：二维码渠道表
- `qr_scan_logs`：扫码记录表
- `conversation_sessions`：会话主表
- `message_receipts`：消息已读/投递回执
- `online_status`：在线状态表或 Redis 映射
- `visitor_devices`：访客设备表
- `ip_blacklist`：IP 黑名单表
- `upload_files`：统一文件表
- `message_attachments`：消息附件关联表
- `audit_logs`：后台操作审计表

### 3. 数据库结论

数据库能支撑基础客服系统，但不适合直接支撑高并发、二维码渠道归因、多端消息同步和精细化已读未读。

建议：

- 全部核心表迁移到 InnoDB。
- `wolive_chats` 增加 `session_id`、`msg_type`、`payload_json`、`sender_type`、`sender_id`。
- 未读统计独立化。
- 在线态放 Redis。
- 黑名单独立成表。
- 二维码渠道独立建模。

## 五、性能与并发分析

### 1. Redis 使用情况

未发现业务层实际使用 Redis。

ThinkPHP 配置默认缓存为文件：

- `config/config.php`
- `cache.type = File`

### 2. 并发风险

- WebSocket 单进程。
- 在线状态保存在进程内存和数据库字段。
- 会话列表依赖 MySQL 聚合查询。
- `getchats` 存在较重查询和数组处理。
- `wolive_chats` 为 MyISAM。
- 消息发送是 HTTP 写库后同步调用推送。
- 文件缓存不适合多实例部署。
- `@ini_set("memory_limit",'-1')` 暴露出历史性能隐患。

### 3. 并发能力评估

- 小规模：几十到几百在线，可通过服务器配置和 SQL 优化勉强支撑。
- 中等规模：几百到一千在线，需要 Redis、索引优化、WebSocket 重构。
- 大规模：上千在线、多客服、多租户，不建议沿用当前架构。

### 4. 优化建议

- Redis 存在线状态、客服连接、访客连接、未读计数。
- WebSocket 服务支持多进程和多机。
- 消息写入异步化，推送和入库解耦。
- `wolive_chats` 改 InnoDB 并按 `business_id/session_id/cid` 建索引。
- 会话列表使用预聚合字段，不要每次聚合消息表。
- 历史消息分页使用游标。
- 附件走对象存储。
- 日志和审计异步写入。

## 建议开发方案

### 1. 最合理二开方案

不要直接在旧代码上堆功能。建议新建项目，按模块逐步迁移：

第一阶段：

- 梳理旧表和业务流程。
- 建新库或新表。
- 实现登录、商户、客服、访客、会话、消息。
- 实现 H5 扫码进入聊天。

第二阶段：

- 实现 WebSocket 实时通信。
- 实现 Redis 在线态。
- 实现已读未读。
- 实现图片、视频、文件消息。

第三阶段：

- 实现二维码渠道管理。
- 实现 IP 黑名单。
- 实现自动欢迎语。
- 实现客服分配策略。
- 实现统计和审计。

第四阶段：

- 数据迁移。
- 压测。
- 安全加固。
- 灰度上线。
